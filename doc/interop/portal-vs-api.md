# OpenEMR Auth Surfaces — Core UI vs Portal vs API

OpenEMR has three independent authentication surfaces, each with its
own session, cookie, password store, MFA strategy, brute-force
protection, ACL, and logout flow. This document compares them
side-by-side so the differences are explicit and any new
authentication code in a derivative work can pick the right model.

| Surface | Code path | Cookie name | Password store | ACL | MFA | Brute-force | Logout |
|---------|-----------|------------|----------------|-----|-----|-------------|--------|
| Core UI (provider/staff) | `interface/main/main_screen.php` and `interface/login/login.php` | `OpenEMR` (or `PortalOpenEMR` for admin) | `users_secure.password` | `AclMain::aclCheckCore` | TOTP, U2F, backup codes | Counter-based lockout | `authCloseSession` |
| Onsite patient portal | `portal/index.php` → `portal/get_patient_info.php` | `PortalOpenEMR` | `patient_access_onsite.portal_pwd` | None (the session itself is the ACL — pid is bound) | Optional email one-time code | Counter-based lockout (per username) | `SessionUtil::portalSessionCookieDestroy` |
| REST API (Standard + Portal REST) | `apis/dispatch.php` | None (bearer token) | n/a (OAuth2 access token) | OAuth2 scope (`user/<Resource>.<c\|r\|u\|d\|s>`) | n/a | Token revocation via `TrustedUserService` | `oauth_access_tokens.revoked = 1` |
| FHIR SMART | Same as REST API | Same as REST API | n/a | SMART v2 scope (`patient/<Resource>.<c\|r\|u\|d\|s>` + `launch/...`) | n/a | Token revocation | Same |
| Local API (JS→PHP) | In-EHR AngularJS JS | Same `OpenEMR` cookie as the calling user | n/a (uses the calling session) | Inherits the calling user's `authProvider` ACL | Same as Core UI | n/a (CSRF check via `APICSRFTOKEN`) | Same as Core UI |

The rest of this document goes deeper on each of those rows.

## The four cookie names

OpenEMR has *four* distinct session cookie names, controlled by
`SessionUtil`:

| Constant | Cookie | Used by | Notes |
|----------|--------|---------|-------|
| `SessionUtil::MAIN_SESSION_ID` | `OpenEMR` (default) | Core UI | Provider / staff login |
| `SessionUtil::PORTAL_SESSION_ID` | `PortalOpenEMR` | Patient portal | Set by `portal/index.php` |
| `SessionUtil::API_SESSION_ID` | (no cookie) | REST API | Bearer token only |
| `SessionUtil::ADMIN_SESSION_ID` | (not used in current builds) | Admin tools | Reserved |

The cookie name is selected on `SessionUtil::setAppCookie(...)`
which writes the chosen constant into the `app_cookie` session key.
The login / logout flows set this early so the session variables
are partitioned cleanly.

## Password stores

| Surface | Table | Column | Hash |
|---------|-------|--------|------|
| Core UI | `users` + `users_secure` | `users_secure.password` (added in v6) | bcrypt (cost 10 default) |
| Patient portal | `patient_access_onsite` | `portal_pwd` | bcrypt (cost 10 default) |
| OAuth2 client (symmetric) | `oauth_clients` | `client_secret` (hashed) | bcrypt |
| OAuth2 client (asymmetric) | `oauth_clients` + `oauth_jwt_tracking` | n/a (public-key only) | RSA-SHA384 / RS256 |
| Local API | n/a | n/a (session-bound) | n/a |
| Trusted-user (refresh) | `trusted_user` | (uuid only) | n/a |

The Core UI's `users_secure.password` was added in OpenEMR 7 as part
of a separation of credentials from the `users` table; legacy rows
were migrated from the old `users.password` column. `AuthHash`
(`src/Common/Auth/AuthHash.php`) is the helper that decides which
column to use.

The patient portal's `patient_access_onsite.portal_pwd` is the
hash of the patient-chosen password. The column is `null` when the
account is in pre-registration state (the patient hasn't picked a
password yet, but the email / phone has been verified).

## MFA

| Surface | MFA options | Setup flow |
|---------|-------------|-----------|
| Core UI | TOTP, U2F/WebAuthn, backup codes | `MfaUtils::setupTotp($userId)`, `MfaUtils::setupFido($userId)`, etc. |
| Patient portal | One-time email code (`passaddon`); optional TOTP after registration | `enforce_signin_email` global |
| REST API (user) | n/a — relies on the underlying user account's MFA at token-issuance time | n/a |
| REST API (system) | n/a | n/a |

`MfaUtils` (`src/Common/Auth/MfaUtils.php`) is the unified helper.
The Core UI flow checks `$session->get('authUserID')` against the
user's MFA enrollment and renders the appropriate challenge
page (`interface/mfa/`) before allowing the user to land on
`main_screen.php`.

The portal's email code is configured via the `enforce_signin_email`
global. When enabled, the login form grows a `passaddon` field and
`get_patient_info.php` requires it to be a valid 6-digit code that
was emailed to the patient (or to the staff's verification
address). The code is generated by `CsrfUtils` (re-used for
numerical codes) and recorded in the `email_queue` table.

## Brute-force protection

| Surface | Mechanism | Where it's enforced |
|---------|-----------|---------------------|
| Core UI | Per-username + per-IP counter in `users_secure.fail_count` (or the legacy `users.fail_count`) | `login.php` before `AclMain::authCore()` |
| Patient portal | Per-username counter in `patient_access_onsite.fail_count`; lockout after 5 attempts | `get_patient_info.php` |
| Local API (in-EHR) | CSRF token check (replay-prevention) | `CsrfUtils::verifyCsrfToken` in `LocalApiAuthorizationController` |
| REST API (Bearer) | Token revocation only; no per-username counter because the token is opaque to the user | `TrustedUserService` + `oauth_access_tokens` table |
| OAuth2 client (client_credentials) | `client_id` is rate-limited at the authorize endpoint | `AuthorizationController` |

The Core UI's `fail_count` is reset to 0 on a successful login.
The portal's `fail_count` follows the same pattern. Both are
exposed to the admin via Admin → System → Login Tracking.

## ACL

| Surface | ACL implementation | Where it's checked |
|---------|---------------------|---------------------|
| Core UI | `AclMain::aclCheckCore($section, $value, $username)` (legacy ACL) and `AclMain::aclCheckCoreAdmin($section, $value, $username)` (admin) | Every interface screen calls `if (!AclMain::aclCheckCore(...)) { ... }` at the top |
| Patient portal | None (the patient is the only user role allowed in this cookie domain; the `pid` session key is the only thing that matters) | n/a — any access without `pid` in the session is a 302 to `index.php` |
| REST API (Standard) | `RestConfig::request_authorization_check($request, $section, $value)` translates the legacy ACL check into the bearer-token scope; the scope is then enforced by `AuthorizationListener::onRestApiSecurityCheck` | Every route closure calls `request_authorization_check(...)` |
| REST API (Portal) | Same translation; but only `patient/<Resource>.<c\|r\|u\|d\|s>` scopes are accepted | `AuthorizationListener::onRestApiSecurityCheck` rejects unless `requestUserRole === 'patient'` |
| FHIR | Same scope-based ACL; ACL also bound to `patient/<Resource>...` for patient-role requests | `AuthorizationListener` + per-resource ACL in `FhirGenericRestController` |
| Local API (in-EHR) | Inherits the calling user's ACL | The AngularJS app makes the API call as the user |

`RestConfig::request_authorization_check` (in
`src/RestControllers/Config/RestConfig.php`) is the bridge. The
function:

1. If `request->isLocalApi()` is true, falls through (the
   `LocalApiAuthorizationController` already verified the CSRF
   token and bound the user).
2. Otherwise checks that the access token's scope contains the
   legacy ACL section/value pair (the value is mapped to a SMART
   scope of the form `user/<Resource>.<c\|r\|u\|d\|s>`).
3. Throws `AccessDeniedException` on failure, which is caught by
   the `HttpRestRouteHandler` and turned into a 401 response.

The mapping is kept in `RestConfig::$aclSectionToResourceMap`
(roughly — see the file for the full table). For example:

| ACL section | ACL value | Bearer scope |
|-------------|-----------|--------------|
| `patients` | `demo` | `user/Patient.read` / `user/Patient.write` |
| `encounters` | `auth_a` | `user/Encounter.read` / `user/Encounter.write` |
| `encounters` | `notes` | `user/DocumentReference.read` / `user/DocumentReference.write` |
| `patients` | `med` | `user/MedicationRequest.read` / `user/MedicationRequest.write` |
| `admin` | `users` | `user/User.read` / `user/User.write` |
| `admin` | `super` | `user/*` (super-admin) |

## Logout

| Surface | What "logout" does |
|---------|--------------------|
| Core UI | `authCloseSession()` in `library/classes/Auth.php`. Calls `session_destroy()`, removes the `OpenEMR` cookie, and revokes any `trusted_user` rows for the logged-in `authUserID`. Redirects to `interface/login/login.php?logout=1`. |
| Onsite portal | `portal/logout.php`. Writes an `onsite_portal_activity` row, calls `SessionUtil::portalSessionCookieDestroy()`, and revokes any `trusted_user` rows. Redirects to `/portal/index.php?logout=1`. |
| REST API (user) | The client discards the access token. To invalidate server-side, the client (or the OpenEMR admin) revokes the `trusted_user` row. The next API call fails at `TrustedUserService::isTrustedUser` with `'Refresh Token revoked or logged out'`. |
| REST API (system) | Same as above. |
| FHIR SMART | Same as REST API (user). Additionally, the app can call the SMART revocation endpoint `POST /oauth2/<site>/revoke` to kill the refresh token. |
| Local API | n/a — bound to the calling session, which is destroyed when the Core UI logs out. |

`authCloseSession` is a legacy function that delegates to
`SessionUtil::closeSession()` and then runs the trusted-user
cleanup. The patient portal's `SessionUtil::portalSessionCookieDestroy()`
is a more aggressive variant that also clears the `pid` and
`patient_portal_onsite_two` session keys.

## Cross-surface differences summary

| Concern | Core UI | Portal | REST API | FHIR |
|---------|---------|--------|----------|------|
| Session cookie | `OpenEMR` | `PortalOpenEMR` | none | none |
| Auth | username + password + (TOTP/U2F) | username + password + (email code) | OAuth2 bearer | OAuth2 bearer (PKCE or backend services) |
| ACL | `AclMain::aclCheckCore` | none (pid-bound) | OAuth2 scope | OAuth2 scope |
| `pid` resolved from | `pid` URL param (with care) | `pid` session key | `patientUUIDString` on the request (from access token context) | Same as REST API |
| `userUUID` resolved from | `authUserID` → `users.uuid` | n/a (patient user) | `oauth_user_id` claim → `UuidUserAccount` | Same as REST API |
| Audit | `log_validator` and `audit_master` tables | `onsite_portal_activity` table | `event` table via `EventAuditLogger::newEvent('api', ...)` | Same as REST API |
| Token lifetime | until logout | until logout | `PT1H` access, `P3M` refresh | Same as REST API |
| Token refresh | n/a | n/a | `POST /oauth2/<site>/token` `grant_type=refresh_token` | Same as REST API |
| Rate-limit | login counter | login counter | none built-in (deployer adds at the LB) | none built-in |
| Federated login (SAML, OIDC IdP) | supported via `interface/sso/` | not supported | n/a | n/a (the app *is* the IdP) |
