# Pending Approvals End-to-End Review

**Date:** 2026-07-14  
**Product:** Ozzyl HMS / HMS SaaS  
**Scope:** Reception cash handover, unified approval API, Approval Center worklist, detail drawer, approval actions, summary/counts, audit trail, tests, and UX.

## Executive conclusion

The reported behavior is confirmed and is not an isolated UI defect.

The current system deliberately sends every receiver-confirmed counter handover to admin final verification, even when the receiver counted the full expected amount and there is no dispute. That old rule is enforced in the cash-accept write path, repeated in the Approval Center query adapter, reflected in policy text, and locked in by integration tests.

A second defect makes the resulting cash-handover approval difficult or impossible to approve from the Approval Center: every cash handover is marked as requiring evidence, while the synthetic handover approval row does not provide an evidence attachment. The frontend therefore marks it as blocked and disables Approve. Cash handovers are also prohibited from using Request Info, creating a dead-end state where the reviewer may only reject the handover.

The correct target behavior is:

- A handover with `counted amount = expected amount`, no due mismatch, and no explicit dispute is a completed operational transfer. It should be recorded in the immutable handover/audit timeline and must not enter Pending Approval.
- A handover with a non-zero variance or explicit dispute is a decision-required exception. It should enter Pending Approval as a `cash_variance`/disputed handover, show the complete evidence generated by the receiver count, and support an admin decision.
- Pending Approval should contain only items that require a human decision. Informational and successfully completed operations belong in Audit/History.

## Product snapshot

### Current backend flow

1. The receiver submits a counted amount.
2. The counter route calculates `variance = receivedAmount - expectedReceived`.
3. It identifies a dispute when variance is non-zero or a dispute reason is provided.
4. It correctly distinguishes the operational handover status as `receiver_verified` or `disputed`.
5. However, both branches set `admin_verification_status = pending_admin`.
6. The Approval Center reads all `receiver_verified` and `disputed` rows with `pending_admin`, without checking variance.
7. The rows are converted to synthetic `cash_handover` approvals and merged with real `approval_requests` and expense rows.

### Current frontend flow

- The page loads a global summary and a paginated worklist.
- Cash handovers are displayed as synthetic approvals.
- The backend enrichment marks cash handovers as evidence-required.
- The synthetic row has no attachment/evidence field, so its evidence status becomes `missing`.
- The drawer disables Approve for missing evidence.
- Request Info is unavailable for cash handovers.
- Several KPI buttons show a global count but apply their actual filter only to the currently loaded page.

## Confirmed root causes

### P0-1 — Clean handovers are intentionally queued for admin approval

**Evidence**

- `src/routes/tenant/billingCounter.ts:1601-1616` calculates the variance, detects disputes, and chooses either `disputed` or `receiver_verified`.
- `src/routes/tenant/billingCounter.ts:1644`, `1765`, and `1894` bind `pending_admin` for the handover regardless of the clean/disputed branch.
- `src/routes/tenant/approvals.ts:687-702` defines a pending handover as either `receiver_verified` or `disputed` with `pending_admin`; it has no non-zero-variance condition.
- `test/integration/routes/billing-counter-handover-admin-verification.test.ts:48-80` explicitly asserts that a zero-variance 1500/1500 handover remains pending for admin.
- `test/integration/routes/approvals.test.ts:513-547` explicitly expects a zero-variance receiver-verified handover in the pending list.

**Impact**

- Admin queue pollution.
- False pending counts and SLA alerts.
- Routine receptionist-to-receptionist transfers consume admin time.
- Staff perceive an already completed transfer as unfinished.
- The approval center stops representing genuine exceptions.

**Required correction**

Change the state transition at the cash-accept write path, not only the list query:

| Receiver outcome | Handover status | Admin verification | Pending Approval |
|---|---|---|---|
| Exact count, no dispute | `received` (or completed equivalent) | `not_required`/`verified_by_rule` | No |
| Non-zero variance | `disputed` | `pending_admin` | Yes |
| Explicit dispute with zero numeric variance | `disputed` | `pending_admin` | Yes |
| Stale/concurrent acceptance | no transition | unchanged | No duplicate |

The existing `cash_handover_verification_events` table should retain the receiver verification as the audit source of truth.

### P0-2 — Cash-handover approval is blocked by an impossible evidence rule

**Evidence**

- `src/routes/tenant/approvals.ts:163-172` places every `cash_handover` in `EVIDENCE_REQUIRED_TYPES`.
- `src/routes/tenant/approvals.ts:220-224` returns `missing` when required evidence is absent.
- `src/routes/tenant/approvals.ts:739-789` builds the synthetic handover row but supplies no evidence/attachment.
- `web/src/components/admin/ApprovalDetailDrawer.tsx:166-175` treats missing evidence as a blocker.
- `web/src/components/admin/ApprovalDetailDrawer.tsx:191-203` disables Approve when blocked.
- `web/src/components/admin/ApprovalDetailDrawer.tsx:169` disallows Request Info for cash handovers.

**Impact**

The reviewer can reach a pending handover, but Approve is disabled and the missing evidence cannot be requested from that screen. This directly explains reports that valid pending items cannot be approved.

**Required correction**

- Clean handovers must not be approval items.
- For a disputed handover, the receiver-count record itself is system evidence: expected amount, counted amount, variance, receiver, workstation, timestamp, and remarks.
- External file evidence should be optional unless a tenant policy explicitly requires it.
- The API should return `blocked_reasons` and `available_actions`; the UI must never present a disabled action without a valid recovery path.

### P0-3 — Approval summary and actions are based on different source models

The page merges:

1. real `approval_requests`,
2. synthetic `billing_handovers`, and
3. synthetic `expenses`.

Each source has different review endpoints, event stores, enrichment, and status semantics.

**Evidence**

- `src/routes/tenant/approvals.ts:1214-1231` merges the sources for summary.
- `src/routes/tenant/approvals.ts:1333-1391` merges them independently for the list.
- `web/src/pages/admin/PendingApprovals.tsx:791-829` uses three separate mutation paths for core approval, handover, and expense.
- `web/src/pages/admin/PendingApprovals.tsx:627-633` deliberately excludes handovers and expenses from the approval-event endpoint.

**Impact**

- Count/list/history drift.
- Different rows expose different levels of evidence and audit history.
- A row can look actionable in the list but be blocked in its source-specific action path.
- Synthetic rows can share the same numeric ID as a core approval, causing ambiguous references and duplicate React keys.

**Required correction**

Keep the existing source tables for now, but introduce one normalized adapter contract:

```text
approval_key: "approval:123" | "handover:123" | "expense:123"
source
source_id
canonical_type
status
is_decision_required
available_actions[]
blocked_reasons[]
policy
amount/expected/count/variance
evidence[]
events[] or detail_url
```

All frontend keys, selections, detail routes, and mutation routing should use `approval_key`, not a bare numeric ID.

## High-priority functional findings

### P1-1 — KPI buttons do not reliably show all matching records

The summary cards contain global counts, but most filters are applied client-side after a single page of up to 50 rows is fetched.

**Evidence**

- `src/schemas/approval.ts:61-68` supports only type, status, execution status, page, limit, and search.
- `web/src/pages/admin/PendingApprovals.tsx:616-625` sends only execution-failed as a specialized backend filter.
- `web/src/pages/admin/PendingApprovals.tsx:744-770` applies high risk, SLA breached, due soon, blocked, missing evidence, and info requested to the current page in memory.

**Impact**

Clicking a card can show fewer rows than its count, or show no row even though the card reports items. It also forces the user to search manually, matching the reported UX problem.

**Required correction**

Add server-side query filters:

- `risk=high`
- `sla=breached|due_soon`
- `decision=actionable|blocked`
- `blockedReason=missing_evidence|execution_failed|needs_info`
- `evidenceStatus=missing|provided`
- `infoStatus=requested|submitted`

Every KPI click must:

1. switch to Pending when appropriate,
2. clear conflicting filters,
3. reset page to 1,
4. send the filter to the server,
5. show the total and paginated matching rows.

### P1-2 — Cash Handover KPI can remain on the wrong status/filter

`setActiveTab('Cash Handover')` changes only the type tab and page. It does not guarantee Pending status or clear an existing KPI filter.

**Evidence:** `web/src/pages/admin/PendingApprovals.tsx:602-614` and `1053`.

**Impact:** Clicking Cash Handover while viewing Approved, Rejected, or another health filter may not display the pending handovers represented by the card.

### P1-3 — “Review oldest first” is not a true global oldest-first queue

The API fetches a page ordered by newest first; the frontend then priority-sorts only the rows already present on that page. The button changes filters but does not request a global oldest-first order.

**Evidence:**

- `src/routes/tenant/approvals.ts:1355-1364` orders by newest before pagination.
- `web/src/pages/admin/PendingApprovals.tsx:770` sorts the loaded rows only.
- `web/src/pages/admin/PendingApprovals.tsx:992-997` does not set a server-side sort.

**Impact:** Older urgent records on later pages can remain hidden while the interface claims to review oldest first.

### P1-4 — Handover audit details exist in storage but are not visible in the drawer

Migration `migrations/0379_cash_handover_admin_verification.sql:15-34` creates structured verification events containing actor, role, expected amount, counted amount, variance, decision, remarks, workstation, and timestamp.

The Approval Center excludes cash handovers from `/api/approvals/:id/events` and does not load a handover-specific timeline.

**Impact:** The reviewer cannot see all information by clicking the row, even though the required audit evidence is already stored.

**Required correction:** add a normalized detail endpoint or a handover-event adapter so one click opens all business data and all event history.

### P1-5 — Reviewed-today KPI is incomplete across sources

`todayApproved` and `rejectedToday` are calculated only from `approval_requests`, while pending totals include handovers and expenses.

**Evidence:** `src/routes/tenant/approvals.ts:1233-1265`.

**Impact:** The dashboard denominator and resolution metrics use different populations.

### P1-6 — Expense enrichment is inconsistent between summary and list

Summary enriches expenses through the generic approval enrichment path, but the list combines the raw expense adapter rows.

**Evidence:**

- Summary: `src/routes/tenant/approvals.ts:1226-1231`.
- List: `src/routes/tenant/approvals.ts:1351-1353` and `1388`.

**Impact:** evidence/policy/SLA/actionability can differ depending on whether the same expense is viewed in a summary-derived KPI or the worklist.

### P1-7 — Generic cash-handover terminology hides the actual exception

A clean transfer and a cash shortage/overage are both shown as `cash_handover`. The pending row reason is generically “waiting for admin final verification”.

**Required correction:** only exceptions should be queued and they should use explicit labels such as:

- Cash Shortage
- Cash Overage
- Receiver Dispute
- Counter Handover Variance

The row should show expected, counted, signed variance, variance percentage, sender, receiver, counter/session, and reason without opening raw JSON.

## UX findings

### P1-8 — The page is overloaded for the primary decision task

The page currently includes:

- a cockpit,
- approximately ten KPI cards,
- four additional triage cards,
- four status buttons,
- search,
- seven health-filter buttons,
- eleven type tabs,
- a thirteen-column desktop table,
- bulk controls,
- pagination,
- and a large multi-section drawer.

This duplicates controls and makes every metric compete for attention. It conflicts with the operational requirement that a receptionist/admin should click a category and immediately see the relevant records.

### Recommended simplified information architecture

#### Header

- Approval Center
- Refresh
- Audit/History link

#### Primary cards — maximum four

1. **Pending Decisions**
2. **Cash Variance / Disputes**
3. **Blocked / Needs Information**
4. **Resolved Today**

#### Worklist toolbar

- Status segmented control: Pending | Approved | Rejected | All
- One search field
- Type dropdown
- More Filters drawer
- Active-filter chips with Clear All

#### Worklist columns

1. Priority / age
2. Type
3. Reference and context
4. Requested by
5. Amount or variance
6. Blocker/status
7. Review action

Advanced policy/evidence fields should remain in the drawer, not permanently occupy table columns.

#### Detail drawer

Clicking any row should show all relevant information without another search:

- decision summary,
- source and unique reference,
- requester/sender/receiver,
- patient/bill/counter/session links where applicable,
- expected/count/variance,
- reason and remarks,
- evidence checklist,
- complete event timeline,
- before/after impact,
- exact available actions,
- exact blocking reason and recovery action.

The drawer should be type-aware; it should not display irrelevant generic sections for every type.

## Edge cases that the corrected design must handle

1. Counted amount differs by floating-point rounding only; compare money in minor units or rounded decimal cents.
2. Receiver enters the same amount but supplies an explicit dispute reason; it must remain disputed.
3. A handover has a due amount; define whether expected receiver cash is gross handover or net receivable and use one formula everywhere.
4. Two receivers/admins submit concurrently; conditional update must allow only one state transition.
5. A receiver accepts after the source session or target session changed; reject stale context.
6. Sender and receiver are the same user; continue to prevent self-handover.
7. Admin is also sender or receiver; enforce separation of duties for variance decisions.
8. Legacy rows have `receiver_variance = NULL`; derive from counted minus expected before classifying.
9. Legacy clean rows are already stuck in `pending_admin`; provide a safe backfill/repair migration.
10. A handover ID equals an approval-request ID; composite `approval_key` prevents UI/event/action collisions.
11. Evidence is generated by the system but external attachment is absent; generated evidence must satisfy the policy.
12. A disputed handover is rejected for recount; preserve the previous count and append a new event rather than overwriting history.
13. Summary load succeeds while one adapter fails; return explicit partial-data status rather than silently inconsistent counts.
14. Search/filter changes during an in-flight request; query keys must contain all filters to prevent stale cache collisions.
15. A KPI has more than one page of results; card count and paginated list total must come from the same query definition.

## Implementation approaches

### Option A — Minimal patch

- Exclude zero-variance receiver-verified rows from pending queries.
- Remove the evidence blocker for cash handovers.
- Update tests.

**Benefit:** fastest.  
**Risk:** leaves the underlying row stuck in `pending_admin`, keeps summary/list/detail fragmentation, and can hide bad state rather than correcting it.

### Option B — Stabilize the complete flow — Recommended

- Correct the cash-accept state transition.
- Queue only variance/dispute rows.
- Treat receiver-count events as evidence.
- Add composite normalized approval keys and a unified detail contract.
- Move KPI filters server-side.
- Simplify the Approval Center layout and type-aware drawer.
- Repair legacy zero-variance pending rows.
- Update backend, frontend, integration, and UI tests.

**Benefit:** fixes the reported failures at their source without requiring a full platform rewrite.  
**Risk:** touches several coordinated modules and requires careful migration/testing.

### Option C — Full Approval Center V2

Move all source types into a new unified approval request, decision, evidence, and event model.

**Benefit:** strongest long-term architecture.  
**Risk:** too large for the current bug cycle and creates migration/rollout risk.

## Selected improvement target

**Option B: Stabilize the complete decision flow.**

The first implementation slice should be **Cash handover decision eligibility and audit correctness**, because it removes false pending items and unblocks real discrepancy decisions. The second slice should be **server-side queue filtering and simplified detail UX**.

## Acceptance criteria

### Cash handover

- Exact-count, undisputed handover does not appear in Pending Approval.
- Exact-count handover records receiver verification in handover events and general audit logs.
- Exact-count handover appears in completed handover history/audit views.
- Non-zero variance appears in Pending Approval exactly once.
- Explicit dispute appears in Pending Approval even when numeric variance is zero.
- Pending variance row shows expected, counted, variance, sender, receiver, session/counter, reason, and event timeline.
- Admin can approve or reject a variance from the drawer.
- The UI never blocks approval solely because no external attachment exists when system-generated receiver evidence is complete.
- Sender/receiver cannot approve the same variance.
- Concurrent decisions cannot both succeed.

### Approval Center

- Every KPI/card click changes to the correct status and server-side filter.
- Card count equals the paginated list total for the selected filter.
- All matching items are reachable through pagination without manual search.
- Rows have source-safe composite keys.
- Every row click displays all source-specific detail and audit events.
- Disabled actions state the exact blocker and provide a valid next step.
- Pending totals include only decision-required items.
- Approved/rejected-today metrics include every source represented by pending totals.
- The main worklist uses a reduced, decision-focused layout.

## Required test changes

### Replace incorrect existing expectations

- Remove/replace the test asserting that a zero-variance receiver-confirmed handover stays `pending_admin`.
- Remove/replace the test asserting that a zero-variance receiver-verified handover appears in the pending approval list/count.

### Add backend tests

- zero variance + no dispute -> completed, not queued, audit event present;
- non-zero variance -> disputed, pending admin, queued once;
- zero variance + explicit dispute -> pending admin;
- legacy NULL variance classification;
- stale/concurrent accept and admin decision;
- source-safe ID collision;
- summary/list/filter totals remain consistent;
- handover detail returns complete event evidence;
- repaired legacy clean pending rows no longer enter the queue.

### Add frontend tests

- clean handover is absent from Pending;
- variance row opens a complete type-specific drawer;
- valid variance approval is enabled;
- missing external attachment does not deadlock a system-evidenced variance;
- every KPI click sends the corresponding backend filter and resets conflicting state;
- Cash Handover/Variance card switches to Pending;
- multi-page filtered results remain reachable;
- duplicate numeric IDs from different sources render and act independently;
- exact blocker and recovery message are displayed.

## Scope boundaries

This stabilization should not introduce multi-level approvals, policy simulation, MFA approval, audit export, or a full new approval schema. Those belong to a later Approval Center V2 initiative.

## Implementation gate

No production code was changed during this review. The next step is to approve this target design, then create an implementation plan divided into:

1. cash handover state machine and legacy repair,
2. normalized approval adapter/detail API,
3. server-side filters and metric consistency,
4. simplified Approval Center UI/UX,
5. regression and acceptance tests.
