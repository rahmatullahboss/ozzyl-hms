# IPD Admission Time and Patient List Canonical-Compatible Design

## Problem

The IPD running-bill patient picker currently has two defects:

1. Admission time can display exactly six hours early.
2. Patient identity and operational metadata are too faint and the name, age, and address wrap onto separate lines.

The time defect is not presentation-only. Legacy admission creation currently has mixed timestamp semantics:

- `src/routes/tenant/reception.ts` omits `admission_date`, so D1 applies `datetime('now')`, producing a UTC-naive value such as `2026-07-29 05:46:53`.
- `src/routes/tenant/admissions.ts` generates a Bangladesh wall-clock naive value by adding six hours before storing it.
- Custom admission dates may arrive as explicit ISO timestamps with `Z` or an offset.
- Canonical admission continuity currently treats every naive legacy value as Bangladesh wall time.

Therefore a UTC-naive legacy row can be projected into canonical storage with the wrong instant and can also be rendered six hours early by legacy UI adapters.

## Canonical and Modular-Monolith Contract

Canonical encounters already require `started_at_utc` as an explicit UTC ISO timestamp. The stable cross-boundary contract will therefore be:

- storage/provider boundary: explicit UTC ISO timestamp;
- API presentation field: `admitted_at_utc`;
- display boundary: format `admitted_at_utc` in `Asia/Dhaka`;
- legacy `admitted_date` remains temporarily for backward compatibility only.

A small admission-time normalization module will sit outside route files and outside the canonical implementation details. Both legacy API adapters and canonical admission continuity will consume this shared module. This preserves a modular-monolith replacement point: the current legacy provider can later be replaced by a canonical encounter provider without changing the frontend contract.

## Legacy Timestamp Classification

The normalizer will accept:

- `admission_date`;
- optional `created_at` evidence;
- optional explicit source semantics for known write paths.

Rules:

1. Explicit `Z` or numeric-offset timestamps are parsed as their stated instant.
2. Date-only values are interpreted as Bangladesh midnight for compatibility with the existing canonical rule.
3. Naive timestamp with known `utc` semantics is interpreted as UTC.
4. Naive timestamp with known `asia_dhaka` semantics is interpreted as Bangladesh wall time.
5. For historical rows with no source marker, compare naive `admission_date` and D1-generated `created_at`:
   - near-equal values indicate the D1-default UTC-naive path;
   - admission time approximately six hours ahead of `created_at` indicates the Bangladesh wall-clock path.
6. Ambiguous rows retain the existing Bangladesh-wall-time fallback rather than silently changing historical meaning.

No production data migration is part of this change.

## Write-Path Correction

New writes must stop adding new ambiguity without changing the legacy field format in a way that could break existing SQLite string comparisons:

- Reception admission creation will explicitly provide the same Bangladesh wall-clock naive format already used by the general admissions route instead of relying on D1 `datetime('now')`.
- The general admissions route keeps the established Bangladesh wall-clock naive legacy storage convention.
- Canonical continuity converts that legacy value to explicit UTC ISO before writing `started_at_utc`.
- API presentation adapters expose explicit UTC ISO through `admitted_at_utc`.
- Custom explicit timestamps remain accepted and are normalized at canonical/API boundaries.

The legacy field convention is therefore uniform during transition, while the stable provider contract remains explicit UTC. The change will preserve legacy SQL compatibility and will not promote canonical reads or disable legacy authority.

## API Changes

`/api/ip-billing/patients` and admission detail responses will expose `admitted_at_utc` generated by the shared normalizer. Queries will include `a.created_at` as normalization evidence where required.

Existing `admitted_date` remains in responses during the transition.

## UI Changes

In the IPD running-bill picker:

- Identity line: `Name • Age • Address` on one non-wrapping line.
- Name, age, and address use the same font size, weight, and foreground colour.
- The line truncates with an ellipsis when space is insufficient; it does not wrap.
- PID, ward, bed, and doctor metadata use a darker, readable colour and `font-medium`.
- Admission date/time uses `admitted_at_utc`, renders in `Asia/Dhaka`, and uses readable contrast and weight.
- The selected-patient summary follows the same identity and contrast rules.

## Tests

Regression coverage will verify:

1. UTC-naive reception row `2026-07-29 05:46:53` with matching UTC `created_at` normalizes to `2026-07-29T05:46:53.000Z` and displays `29-07-2026 11:46:53 AM` in Dhaka.
2. Dhaka-naive row normalizes to the correct UTC instant.
3. Explicit `Z` and `+06:00` timestamps preserve the correct instant.
4. Canonical admission continuity uses the same normalizer as legacy API presentation.
5. API responses contain `admitted_at_utc` while retaining `admitted_date`.
6. The patient identity line renders name, age, and address in order within one no-wrap container.
7. Metadata and admitted time use the stronger readability classes.

## Safety and Cutover Compatibility

- No historical rows are rewritten.
- No canonical-read promotion is performed.
- Legacy authority and non-blocking canonical shadow policy remain unchanged.
- The normalized UTC API contract is the future canonical provider contract, preventing another frontend change at legacy shutdown.
- Existing unrelated dirty work is not touched.
