# Patient AI Planner Design

## Goal

Add a patient-facing AI planner inside the patient portal that lets a patient manually request a structured health guidance plan based on their existing records, uploaded documents, and self-reported data.

The planner must:

- generate only when the patient asks
- save plans persistently with history
- show plans in a polished card-based interface
- enforce a free-tier daily generation limit
- provide basic lifestyle, food, exercise, and follow-up suggestions
- clearly state that the output is not a diagnosis and does not replace a doctor

## Product Decision

This feature is global-patient scoped, not hospital scoped.

That means the plan is based on:

- linked hospital records
- patient vault documents
- patient-reported conditions, allergies, medications, lifestyle logs, and vitals
- cross-hospital summaries already available to the patient account

This is the correct first version because it remains useful even before hospital partners are onboarded.

## Reference Patterns

The first version should follow patterns seen in high-level wellness and health apps:

- persistent plan surfaces rather than temporary chat output
- structured sections instead of one long AI paragraph
- safety-first framing like symptom assessment apps
- clear next actions and warnings
- easy later refinement without rebuilding the whole system

## User Flow

### Entry

The patient opens a dedicated `AI Planner` area in the patient portal.

They see:

- the latest active saved plan, if one exists
- previous plans in history cards
- a button to generate a new plan
- a remaining free-use message for today

### Generation

When the patient clicks generate:

1. the backend resolves the authenticated global patient identity
2. the backend gathers relevant patient data from global and linked sources
3. the backend sends a structured prompt to the AI
4. the AI returns valid JSON in a fixed schema
5. the plan is saved to D1
6. the new plan becomes the current active plan
7. the patient sees the plan rendered as cards

### History

Older plans remain visible in history and can be reopened later.

The system keeps history rather than overwriting old plans.

## AI Output Shape

The AI response must be structured JSON.

It should contain:

- `headline`
- `summary`
- `focus_areas`
- `eat_more`
- `avoid_or_reduce`
- `daily_routine`
- `exercise_plan`
- `follow_up_actions`
- `warning_signs`
- `doctor_consultation_advice`
- `disclaimer`
- `confidence`
- `data_gaps`

The output must avoid definitive diagnosis language.

## Safety Rules

The AI must:

- never claim to diagnose disease
- never tell the patient to stop prescribed medication on its own
- avoid strong recommendations when data is sparse
- say when a doctor should be consulted
- explicitly mention urgent-care escalation when warning signs are present

The UI must clearly show that this is basic guidance only.

## Free-Tier Limit

The patient can generate one full AI plan per day for free.

The system should enforce this by checking the number of plans generated by the same global patient identity on the current calendar date.

Later refinement or paid limits can be added later, but are not part of this first version.

## Persistence Model

Create a dedicated D1 table for patient plans.

Each row stores:

- the global auth user id
- the patient UHID snapshot
- an optional patient name snapshot
- plan status
- generated plan JSON
- source data snapshot JSON
- plan summary fields for fast listing
- timestamps

This gives:

- durable saved plans
- history
- auditability of what data the AI saw
- support for later regeneration and comparison

## Data Inputs

The planner should aggregate:

- cross-hospital dashboard appointments and prescriptions
- linked hospital summaries using existing portable health summary builder
- patient vault document metadata
- patient-reported data
- adverse reactions
- lifestyle logs
- vitals

The system does not need OCR or full document parsing in V1. Metadata and existing structured records are enough.

## Backend Design

Add a reusable planner library that:

- resolves patient-linked data
- builds a compact AI input snapshot
- builds the AI prompt
- validates the returned JSON
- normalizes the plan for storage and rendering

Add global patient routes:

- `GET /api/global-portal/ai-plans`
- `GET /api/global-portal/ai-plans/:id`
- `POST /api/global-portal/ai-plans/generate`

## Frontend Design

Add a new patient portal tab: `AI Planner`.

The tab shows:

- hero card with latest plan headline and summary
- section cards for food, avoid, routine, exercise, follow-up, and warnings
- history cards for older plans
- generation CTA
- daily limit state
- loading and empty states

The visual language should feel like a premium wellness app, not a raw hospital table.

## Error Handling

If AI is unavailable:

- do not create a partial plan
- show a clean retry message

If the daily limit is reached:

- return `429`
- show a patient-friendly limit message

If the patient has too little data:

- generation may still work
- the plan should explicitly include `data_gaps`
- confidence should be lower

## Testing

Add:

- route integration tests for listing and generation
- limit enforcement tests
- planner normalization tests
- UI helper tests for plan cards

## Out Of Scope

Not in this first version:

- automatic daily generation
- doctor AI assistant
- OCR for uploaded files
- editable AI conversation threads
- paid subscription logic
- real clinical diagnosis support
